## 改进条目（按编号）

## I025: M33 B+Tree 节点级锁

- **分类**: 并发 / 锁
- **背景**: 每次操作 lock 整棵树
- **方向**: Semaphore 限流 + latch coupling（crabbing protocol）
- **依据**: 2026-09-14 用户指令归入长期方向（依赖 I024 键编码评估）；已纳入 MS55 路线。
- **影响**: B-Tree 并发写争用与单页操作粒度；不改索引格式与行为面。
- **依赖**: M23（I024）
- **状态**: promoted（已纳入 MS55 路线「索引页空间与锁」，未实施；MS55 为 ready）

## I029: M46 瘦内部节点

- **分类**: 性能 / 存储
- **背景**: B+Tree 内部节点只存 separator keys，不存完整 Key
- **方向**: 内部节点改为可存完整 Key 的瘦节点布局；格式变更须先写明旧库兼容路径，收益未盖过兼容成本时保持原格式
- **依据**: 2026-09-14 用户指令归入长期方向（依赖 I024）；已纳入 MS55 路线。
- **影响**: 索引页空间占用与树高；格式变更须先写明旧库兼容路径。
- **难度**: 高，需重构 B+Tree 分裂/合并逻辑
- **依赖**: M23（I024）
- **状态**: promoted（已纳入 MS55 路线「索引页空间与锁」，未实施；MS55 为 ready）

## I030: M47 合并 Tag byte

- **分类**: 性能 / 序列化
- **背景**: Slot Tag byte 合并进 VersionHeader，省 1 byte/slot
- **方向**: 把 Tag byte 并入 VersionHeader 布局，每 slot 省 1 byte；须先评估对序列化格式兼容性的影响
- **依据**: 2026-09-14 用户指令归入长期方向；已纳入 MS55 路线。
- **影响**: 每 slot 的序列化开销（1 byte/slot）与格式兼容成本。
- **难度**: 低，但影响序列化格式兼容性
- **状态**: promoted（已纳入 MS55 路线「索引页空间与锁」，未实施；MS55 为 ready）

## I049: 现有 WAL 组提交收益评估

- **分类**: 性能 / WAL
- **背景**: 历史条目按「缺少组提交」登记，但当前已有 `WALBuffer::append_commit_and_wait`、后台 `do_flush` 与 `WalWriter::write_batch`；`TransactionManager::commit` 已等待持久化通知，不能重复建设。
- **方向**: 只在实际存在同一数据库实例内并发提交、且 fsync 是瓶颈时评估现有合并率、等待与吞吐。串行 one-shot 场景下，`openspec/changes/archive/2026-11-10-ms47-typed-batch-write/` 已裁定不新增入口，I077 的持锁窗口余项仍未排期。
- **依据**: 2026-10-18 静态核对 `src/wal/buffer.rs`、`src/wal/writer.rs`、`src/transaction/manager.rs`；本次未测量多事务合并率。
- **影响**: 同实例并发提交场景下的 fsync 瓶颈与等待开销；串行 one-shot 形态无收益。
- **前置**: 保留先量化再决定的纪律；与任务台账中串行单写者模型下排除组提交优化的说明一致。
- **状态**: planned（2026-10-23 自 MS22 退回，未承诺、未排期。串行单写者下无并发提交可攒，不作为当前收益项；同实例并发提交出现后再评估。2026-09-14 MS08 剥离退还登记）

## I077: CLI 串行化并发模型（busy-timeout 锁等待 + 持锁窗口治理）

- **分类**: 架构 / 并发与进程形态（嵌入式 one-shot 形态的并发策略）
- **背景**: 登记时并发写同一库立即 `DatabaseLocked` exit 4；该缺口已由锁等待预算解决。剩余候选为长操作持锁窗口，历史 import 样本逐条 auto-commit 约 4.1ms/行、30000 行约 123s 全程持锁，不能当作当前新测结果。
- **方向**: 三件套——① 锁等待策略可配置：`--busy-timeout` / env / lib 三通道（沿用 `RTSQL_KEY`/`RTSQL_WAL_CHECKPOINT_BYTES` 通道先例，复用 `try_lock_with_backoff` 改策略，默认保守值，超时后维持 `DatabaseLocked` exit 4 既有错误面；读共享锁与写独占锁两侧统一生效）；② 长操作持锁窗口治理：import 攒批提交（fsync 次数按批数量级下降），以压缩最长持锁尾。`openspec/changes/archive/2026-11-10-ms47-typed-batch-write/` 已裁定不新增写入口，本项不得另建写路径；③ I071 定位注记已随本条更新——`rtsql serve` 为串行模型达吞吐天花板后的扩容路径，非对立方案
- **依据**: 2026-10-01 用户方向（原话要点：「把一个命令行视为一个原子化的……同一时间多个并发的操作命令行，全都接受但是实际上一个一个不相互干扰地串行实施，就像操作系统底层调度 task 一样……达到假并发，实则高效异步原子化输入……要求数据库足够高效，或者实现一个合理的调度机制」）；设计判断随登记采信——advisory 文件锁本身即跨进程串行化原语（调度器已存在），同步阻塞 CLI 下「队列调度」与「等锁再执行」对调用者不可区分，无需常驻进程；MS18 one-shot 固定开销 ~6.5ms（串行吞吐 ~150 ops/s 量级天花板）；import 量化来源 change `2026-09-30-catalog-durability-and-cli-surface` Iteration 000 Act 实测
- **影响**: 多 agent 并发写场景从硬失败变为全部接受、逐个原子完成（每次调用全程持独占锁，重叠结构性不可能）；语义对齐 SQLite `busy_timeout` 先例；跨进程多写者决策可大幅推迟
- **边界**: 原子单元 = 单次 CLI 调用，跨调用语句序列不构成事务（复合原子性由单次调用内多语句/显式事务承担，MS11-T02 已支持）；flock 非 FIFO，不自造票据队列（公平性诉求留给 I071 扩容路径）；I049 组提交在本模型下无效（串行单写者无并发提交可攒）
- **语义澄清（2026-10-18）**: 上述「单次调用原子」只表示文件锁覆盖的互斥执行窗口，不表示调用内多条 auto-commit 语句全有或全无；事务原子性仍由显式事务及各语句契约决定。批次事务候选原沿已归档的 I021。2026-11-10 `openspec/changes/archive/2026-11-10-ms47-typed-batch-write/` 不新增入口，本条②与 I083 仍未排期，不得另建写路径。跨进程一写多读的结论见 `openspec/changes/archive/2026-11-17-ms52-torn-tree-and-cross-process/`。
- **状态**: promoted（2026-10-01 用户批准重排纳入路线——① busy-timeout → MS28-T01 已交付；② import 攒批/持锁窗口治理于 2026-10-23 随 MS22 退回，未承诺、未排期；③ I071 定位注记已随本条完成；`.agents/docs/tasks.md`）

## I097: 建环一次并在失败时继续 pwritev

- **分类**: 性能 / I/O
- **背景**: MS54 增加了默认关闭的 `io-uring`。启用后，`write_all` 每次调用 `setup_ring`，返回前拆掉环。建环或映射失败发生在写出字节之前，这次数据页写失败，不退回 `pwritev`。检查点、关闭和脏页逐出因此失败。
- **方向**: 打开库时试一次建环。成功则把环留着，连续段和单页都用它提交并等待完成。失败则这个进程继续用 `pwritev`。不把 `io-uring` 放进所有平台的默认 features。单页写出是否更快单独测量，不把连续 64 页的结果算到单页上。
- **依据**: 2026-11-24 在本机 WSL 上，`io_uring_flush_compare` 于计时前完成 `io_uring_setup` 和映射，五次循环复用该环。`uring_ns` 升序后的第三个是 68438，`flush_ns` 升序后的第三个是 157533。该数字只代表这次环境和环已打开的写出，不是当前收益承诺。产品路径见 `src/storage/file_storage.rs` 的 `setup_ring` 与 `write_all`。收尾全量用的是未启用该 feature 的默认构建。
- **影响**: 能建环的 Linux 进程走已打开的环；建不了环的进程仍用 `pwritev`，检查点和关闭不因建环失败而失败。macOS 与默认 `cargo build` 保持现在的写出路径。
- **关联**: `openspec/changes/archive/2026-11-24-ms54-dirty-page-batch-io/` 交付的是默认关闭的 feature。本条不重开那个比较。
- **状态**: open（2026-11-24 用户确认写入。未承诺实施，未排期，未纳入里程碑）
