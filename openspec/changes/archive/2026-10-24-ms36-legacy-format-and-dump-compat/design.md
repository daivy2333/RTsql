# Design：MS36 历史库与 dump 兼容

## D1 支持范围的划分维度是目录行布局代际，不是文件头版本

**决定**：把「旧库」定义为**文件格式版本仍为 v1、但系统表目录行属于旧布局代际**的数据库文件；把「支持范围」按目录行代际 G1/G2/G3 逐代给出能力矩阵。文件头版本只保留两条范围外判定（`format_version > 1` → `NewerFileVersion`；无头文件 → `NotADatabase`）。

**理由**：`FORMAT_VERSION` 自文件头引入（commit `2eda010`，MS10-T03）起一直是 1，从未变过——产品**不存在「更旧的格式版本」**。把旧库说成「旧版本号」会诱导出「运行时伪造版本号」这类错误做法。真实的代际差异只在系统表目录行：`__tables` 行的可选尾段（unique_roots → secondary_indexes → kind 字节）与 `__columns` 行的可选 DEFAULT 段是**逐步追加**的，因此旧行是当前行的**字节前缀**，当前代码用「尾段缺失即取默认」的方式兼容读取。

**代价**：范围表述不再能用「支持版本 ≤ N」一句话概括，需要一张逐代矩阵。这是事实使然，不做简化。

**替代方案（否决）**：在文件头引入 `format_version = 2` 之类的版本号来标记「旧库不支持」。否决理由：这会把「目录行布局差异」误装成文件格式版本变更，且会破坏 `database-file-format-header` 域已记录的「既有 v1 库重开校验通过」语义。

## D2 兼容样本来自仓库内固定字节样本，不在运行期伪造

**决定**：旧库文件样本与旧 dump 文本样本由**更早版本的产品构建**产出，作为**固定字节文件**提交进仓库（`tests/fixtures/legacy/`），测试运行时把它复制到临时目录再打开。**运行期不做任何版本号伪造、不做行布局伪造、不做版本/哈希比对。**

**理由**：任务明确禁止「运行时伪造一个旧版本号」式的样本生产——那是身份伪造式做法，且随实现演进而脆弱。旧构建产出的文件是真实的旧格式产物：它的字节是旧实现按旧布局写出来的，不是当前实现按新规则拼出来的。固定字节样本同时满足「真实」与「可复现」两个要求：测试不依赖旧工具链，旧构建只用于一次性生产。

**旧构建的可得性（本次已验证）**：`git clone` 到隔离目录 → checkout `d8165fc`（2026-09-24，MS23 落库前的最后一个提交）→ `cargo build --offline --bin rtsql` 可在当前工具链（rustc 1.99.1）下成功构建 → 用该二进制建库与 dump。隔离目录在仓库之外，不触碰工作区现场。

**关于「禁止身份机制」**：旧版本构建只用于**生产样本数据**，不是运行身份判定。样本进入仓库后是固定输入；测试运行期不比对任何版本号、哈希、revision 或产物清单。版本判定只发生在产品自身的文件头版本契约里（`FileStorage::open` 的 `decode`），那是产品行为，不是验证机制。

**再生**：样本来源、旧构建命令与样本内容写在 `tests/fixtures/legacy/README.md`；再生产是可选动作（需要旧工具链），不是测试的前置条件。

## D3 旧 dump 没有独立版本号，代际由 DDL 渲染差异标识

**决定**：把「旧 dump」定义为**由旧版本 `rtsql dump` 产出的 SQL 文本**。dump 是纯文本、无自带版本号，其代际特征是 DDL 渲染差异（短类型名 `INT`/`STRING`/`BOOL` 对长名 `INTEGER`/`TEXT`/`BOOLEAN`）。支持范围的判据是「当前解析器与计划期规则能否接受该文本」，而不是「文本里写着哪个版本」。

**理由**：给 dump 加版本头会改变 dump 产物格式（超出 MS36 范围，且破坏既有 `cli-noninteractive-shell` 的 dump 契约）。当前解析器已接受长短两套类型名，既有规格也已写明「多代 dump/restore 幂等 SHALL 保持（解析器接受长名）」，因此文本代际不需要额外的机制来识别。

## D4 范围外一律显式拒绝 + 迁移路径；不改动 restore 的既有提交语义

**决定**：不在支持范围内的输入必须得到**明确、定位到语句的拒绝**（错误文本点名拒绝原因、给出「第 k 条/共 n 条」、退出码 3），并在规格与 README 中给出迁移路径。**不**把 restore 改成「先全量校验再执行」的事务化语义。

**理由**：三类范围外拒绝当前已经显式存在（计划期 `NON-INTEGER PRIMARY KEY` / `UNIQUE (INT columns only)`，执行期 `NOT NULL constraint violation`），且既有规格 `cli-noninteractive-shell` 已把「逐条 auto-commit、失败即停、失败前语句已生效」写成合同。改变它属于功能语义变更，需要独立 change 与独立验收，超出 MS36 已承诺范围（I092 建议里的「明确拒绝或迁移路径」由既有拒绝面 + 文档化迁移路径满足）。

**已知边界（明确记录，不在本 change 修复）**：多表 dump 中若靠后语句被范围外拒绝，靠前语句已生效。这是既有 restore 合同的直接后果，不是新缺陷。

## D5 写入旧库 = 被写到的表的目录行就地升级为当前布局

**决定**：支持范围写明「旧库可写入」时，同时写明写入的格式后果：被写到的表，其目录行被**重写为当前布局**（旧行删除、新行追加到目录链）；未被写到的表保持原代际。升级后旧库仍是合法旧库，可继续打开、查询、写入。

**理由**：`update_table_tail` 走「反序列化 → 修改 → 重新序列化 → `update_field_in_chain` 写回」的整行重写路径；新行比旧行长（多出尾段）时走「追加新副本 + 删除旧副本」，因此升级是既有机制的自然结果，不需要专门实现。写明这一后果是让「可写入」成为可预期合同，而不是让用户意外发现自己的库格式变了。

## D6 打开时重建（MS35）与目录行代际正交，旧库天然满足重建前提

**决定**：把「旧库在当前打开路径（恢复 → 打开时安全重建）上可打开」写进支持范围，并作为样本断言项（断言重建未放弃：打开 stderr 无重建放弃消息、活表数据完整、完整性零 error）。

**理由**：MS35 的重建按**持久目录**推导活页集合：目录链（`__tables`/`__columns`）、表数据链、溢出链、PK/唯一/二级索引树。旧库的目录行正是持久目录的载体，而兼容读分支保证旧行能解析出同样的字段（`data_page_head`、`index_root_page_id`、列定义）；索引根为 0（无该类索引）时 `collect_tree_pages` 返回空集。因此重建的输入前提与目录行代际无关——**代际越旧，重建越依赖兼容读分支，而兼容读分支正是本 change 的断言对象**。

**本次核对结论**：真实 G1 样本（含已释放页的变体、带未决 WAL 的变体）在当前构建上打开成功，无重建放弃消息，活表行完整，`check_integrity` 零 error。详见 `tasks.md` 的 Current-State Evidence。

## D7 一个 G1 样本即覆盖全部向后兼容读分支

**决定**：样本集只取 G1（最旧代际）作为旧库文件样本，不为 G2/G3 单独造样本。

**理由**：G1 是唯一同时缺少全部可选尾段的代际，因此它一次性覆盖当前代码的四个兼容读分支（`__tables` 行的 unique_roots 段缺失、secondary 段缺失、kind 字节缺失，`__columns` 行的 DEFAULT 段缺失）。G2 只在 unique_roots 段上与 G1 不同，G3 完全走原生路径——两者的覆盖面已由既有测试套件承担。样本数少、可读性好，符合「少量样本」的要求。

## D8 不新增产品代码路径：合同以规格 + 刻画断言表达

**决定**：本 change 的产品代码改动为零。新增用例断言的是**当前已经成立**的行为（刻画断言），预期写完即 GREEN；change 的实质产出是规格域 + README 表述 + 固定样本基线。

**理由**：MS36-T01 承诺的是「定义支持范围，并用少量样本断言打开、查询、写入和恢复」；本次调查逐项确认支持范围内行为当前成立、范围外拒绝当前已显式存在（证据见 `tasks.md`）。在没有观察到行为缺陷的前提下引入产品改动会违反 Surgical Changes，并制造「为了改而改」的回归面。

**如果实施中发现样本断言不成立**：那是行为缺陷，按公共规则作为 Issue 候选上报，并由 Plan 决定是否把修复纳入本 change（需要新的执行依据时走 replan）。不在计划阶段预设修复。

## D9 可选改进（不在本 change 范围）

当前 `dump` 对含非 INT `UNIQUE` 列的表无条件渲染 `UNIQUE`，因此「旧库 → dump → 新库 restore」在该类表上会被计划期拒绝（`UNIQUE (INT columns only)`），需要人工按迁移路径改 DDL。参照既有的 PRIMARY KEY 渲染规则（`create_table_sql` 仅在主键列声明类型为 INTEGER 时输出 `PRIMARY KEY`），把非 INT `UNIQUE` 也按同样规则渲染，可以消除该不对称。

**这不是缺陷**（既有行为已在 README 记录），因此不进入 MS36 的 Acceptance；作为可选改进登记，由后续承载 change 决定。本 change 只保证该场景**拒绝明确、迁移路径有文档**。

## D10 全量回归预算与批计划生成规则

**决定**：M19 分批全量回归在本 change 收尾时执行**一次**（全 change 一次预算），记在最后一个 Iteration（001）的 Iteration Plan 与 T4。批纪律沿用 R48：`--lib --bins` 单独成批；`tests/*.rs` 按文件名字典序分组，每批 8–12 个目标；每批一次独立 `cargo test --test <f1> ... -- --test-threads=1` 调用；批间顺序执行；禁止一次无目标过滤的全量调用；禁止默认并行度；全量 Gate 等价于「全部批次各自 0 failed」；记录各批 passed/failed 并与目标清单对账。

**批计划生成规则（本次明确）**：目标清单 = 收尾时 `tests/*.rs` 全部文件 + `--lib --bins`（本次为 135 + 1 = 136 个目标）。文件批数 `B = ceil(文件数 / 12)`；文件按字典序切片，前 `B × 12 − 文件数` 批各取 11 个目标，其余各取 12 个——保证每批落在 8–12 且不重不漏。`--lib --bins` 单独成第 `B+1` 批。

**与 R48 的差异说明**：R48 记的切分算法（「剩余 ≤ 12 则取剩余，否则取 11」）在文件数落到某些余数时会产出不足 8 个目标的末批（例如 134 个文件时的末批为 13，超出 12）。本 change 使用上面的等分规则以同时满足「8–12」与「确定性可复算」。该规则差异作为 Runbook 候选上报，由 `openspec-experience-recorder` 决定是否更新 R48，本 change 不改 Runbook。
