# Design：开放缺陷批（存储/DDL 实质缺陷 + 旧格式兼容证据缺口）

## D1. 承载形态：一个 change、八个逻辑 Iteration

**决策**：12 项候选（10 项承载 + B-3 不承载 + C 组 3 项）放在**一个 change** 内，按根因层分成 8 个逻辑 Iteration（第 7 个 Iteration 005「DML 墓碑的放弃窗口收敛」是实施期新发现的 ISS24 同形面，由 Iteration 001 的 Plan Review 2026-10-25 追加登记；第 8 个 Iteration 006「索引树读路径的有界读与显式拒绝」是实施期新发现的 B-4 同根因层读 / 写热路径面，由 Iteration 002 的 Plan Review 2026-10-25 追加登记；二者与既有 Iteration 同属一次缺陷闭环交付，不另起 change）。

**理由**：

1. **同源同交付模型**：这批候选来自同一次发现波（MS35 / MS36 的 Plan Review + MS34 修复批的遗留 open Issue），用户指令要求「直接寻找好的承载方式流程进行修复而不是等级」——即**一次缺陷闭环交付**，不是一个里程碑。已有先例：`2026-10-24-ms34-issue-fix-index-atomicity-and-ddl-catalog`（ISS20 + ISS21 合并为一个 change、两个 Iteration、共用一次收尾全量）。
2. **验证预算**：`AGENTS.md` 规定高开销验证按 **change** 预算（默认整个 change 一次）。拆成两个 change 会把 M19 分批全量回归的执行次数翻倍，而 C 组**没有产品代码改动**（只加测试目标与固定样本），单独吃一次全量预算收益极低。**一个 change = 一次收尾全量**。
3. **根因耦合度**：C 组的「G2 文件级样本」与「三条常态化用例」共用同一批样本与同一份来源说明（派生量必须与来源说明同步），拆开会切断这条耦合；C 组与缺陷组的唯一交点是「收尾全量的覆盖对账基准」，由 tasks.md 的收尾验证条目统一承载。
4. **诊断边界不冲突**：Iteration 之间按**根因层**切分（索引页归属 / DDL 改写面 / 释放路径读 / 改写窗口读 / 持久化判定 / DML 墓碑写序 / 索引树读路径读 / 兼容证据），每层有独立的失败定位范围与验证入口，互不污染。

**替代方案（已否决）**：

- **按严重等级分 2–3 个 change**（先修 abort 类、再修静默损坏类、最后补证据）：违反用户指令「不按等级搁置」；且会把「同一条根因链上的 ISS22/ISS24」拆到不同批次，ISS24 的归属判定（是否由 ISS22 的链分叉导致）将无法在同一批次内闭环。
- **按发现来源分 change**（MS35 报告的 / MS36 报告的 / ISS 台账的）：发现来源不是根因边界，B-1（B-2 的下游后果）与 B-2 会被拆开。

## D2. B-2 的修复形态：合并掉的右叶页只释放一次

**当前行为**：`btree.rs:583` `merge_leaves` 在 `:610` 释放 `right_id`、在 `:622` 标记释放完成，并把 `right_id` 作为 `MergeInfo.freed_page_id` 返回；`btree.rs:631` `delete_from_internal` 收到该 `MergeInfo` 后调用 `btree.rs:655` `handle_child_merge`，后者在 `:672` **再次** `free_page(merge_info.freed_page_id)`、在 `:675` 再次 `complete_free_release`。

**后果**：`free_page` 把页号推进待释放集合 ⇒ 同一页号出现两次 ⇒ 提升后同一页号在可分配集合里出现两次 ⇒ `allocate_page` 可把**同一页交给两个不同对象** ⇒ 两个对象各自改写同一页 ⇒ 静默损坏。这是 ISS23 的首要候选通路。

**决策**：**被合并掉的右叶页只释放一次**。保留 `merge_leaves` 的释放点（它与「父节点分隔键移除」同属一个写单元，锚点写语义已由 MS35 的 `free-page-lifecycle` 规定），`handle_child_merge` **不再重复释放**该页——它只负责父节点分隔键的移除与随后的 underflow 处理。

**为什么不在 `merge_leaves` 里释放、而在 `handle_child_merge` 里释放**：两处都可行，但 `merge_leaves` 的释放点已经绑定了「锚点写 = 父节点分隔键移除（同一写单元内的树页写），此刻已发出」的完成标记（`:622`）。把释放点后移到 `handle_child_merge` 会改变 MS35 已验收的锚点写语义（`free-page-lifecycle` R1 的判定时点）⇒ **不改已验收语义**是硬约束，故选择在 `handle_child_merge` 侧消除重复释放。

**被否决的替代方案**：

- **让 `free_page` 幂等（同页只入集合一次）**：把「页归属唯一性」的责任从 B-Tree 的调用点移到存储层的集合语义，会改动 MS35 已验收的 `free-page-lifecycle` 语义（释放集合的入队规则），且掩盖调用点的错误。**否决**。
- **在 `merge_leaves` 里不释放、改由 `handle_child_merge` 释放**：改变锚点写时点（见上）。**否决**。

## D3. ISS23 的归属判定协议：先修 B-2，再复现判定

**事实**：`btree.rs:237` `insert_into_page` 的内部节点分支在 `:327` 递归下降；既有 gdb 现场显示 35+ 层同 `page_id` 帧 ⇒ 下降成环 ⇒ 栈溢出、进程 abort。`btree.rs` 自 MS34 修复批以来未被改动，该形态仍在。

**未知**：环的成因。**首要候选**是 D2 的页归属破坏（同一页号被两个节点引用 ⇒ 下降可回到自身）；**不能排除**独立成因（B-Tree 内部节点分裂/分隔键插入路径自身的缺陷）。

**决策（判定协议，非结果）**：

1. 先修 B-2（D2），**再**跑 ISS23 的复现用例。
2. 若复现消失 ⇒ 归属结论为「B-2 的下游后果」，Iteration 000 关闭 ISS23。
3. 若复现仍在 ⇒ **归属结论为独立成因**，须在**同一个 Iteration 000 内**继续定位到具体的下降环（环上的页号序列 + 形成环的那次写入），并修复。**归属结论与定位证据必须写进 Act Response**；若定位所需的执行依据超出当前 Cycle 的 Task Definition 范围（需要新的自包含调查），按 `openspec-plan` 的 Review 分类退回 Plan（`replan-required`），**不得**在 Iteration 000 内顺带扩大范围。

**为什么把判定放在 B-2 修复之后**：B-2 是**读码即可确认**的确定性缺陷，且修复代价小、风险面窄；先修它同时消除 ISS23 的最强候选通路，可把 ISS23 的剩余调查面收敛到「B-Tree 分裂/分隔键路径」。反过来先查分裂路径会同时面对两条候选通路。

**ISS23 的规模约束**：ISS23 触发面约在 300 行以上（登记现场 N=300 / 600 / 2000）。**任何需要更大规模的用例必须先解决 ISS23 本身**——本 change 内不使用 ≥ 300 行的表规模来构造用例（与 `tests/fixtures/legacy/README.md` 已记录的同类约束一致）。

## D4. ISS22 的修复形态：改写路径的单一尾游标

**当前行为**：`src/storage/data/table_manager.rs:734` `alter_drop_column` 的改写循环有两条腿：

- **DELETE 腿**（`:945` 附近）：`write_tuple_to_data_page(&self.buffer_pool, &old, &tombstone, &[])`——直接调用底层写入口，**用旧表 `old.data_page_tail`**；该入口**不做陈旧尾指针自愈、不回写目录尾指针**。
- **INSERT 腿**：`self.write_tuple(&new_meta, &vh, &buf)`——走 `TableManager::write_tuple`（`:2010`），**用窄化副本 `new_meta.data_page_tail`**（`:864` 处从 `old.data_page_tail` **拷贝**的独立 `Mutex`），并做 `heal_stale_tail` 自愈 + 目录尾指针回写。

**故障机制**：两腿各持一条尾游标。页写满时，DELETE 腿在自己的游标上分配新页并把链上 `next` 指针改写为新页；INSERT 腿随后在自己的（陈旧）游标上再分配一个页并**覆盖同一个 `next` 指针** ⇒ 先分配的页成为孤儿 ⇒ 写在其中的已提交行丢失（实测 40 行剩 25）。

**决策**：**改写路径只使用一条尾游标**。具体地：DELETE 腿与 INSERT 腿必须经由**同一条会自愈并回写目录尾指针的写入口**（`TableManager::write_tuple` 的既有语义），使两腿看到同一条链的同一个尾。

**为什么不用「两条游标 + 显式同步」**：显式同步需要在两腿之间搬运尾指针，仍保留「页写满时各自分配」的窗口；单一游标从机制上消除分叉可能。

**为什么 DELETE 腿不能继续直接调底层入口**：该入口不做陈旧尾自愈（`heal_stale_tail` 在 `TableManager::write_tuple` 内），也不回写目录尾指针 ⇒ 即使统一了游标，目录尾指针仍可能落后于链尾。

**对既有行为的影响面**：改写路径的写入口收口会影响「DDL 改写期间的目录尾指针回写时机」。目录**列**的窄化仍在提交点生效（`ddl-catalog-transactional` R1/R2 不变）；**尾指针**是数据链的既有目录字段，其回写时机由本 change 调整为「每条改写写入都回写」。这属于数据面而非目录列定义面，**不与已验收规格冲突**（`ddl-catalog-transactional` 管的是列定义与列数）。

## D5. ISS24 的修复形态方向：判别 M1 / M2，两者都必须闭合

**事实**：被放弃的 `ALTER TABLE DROP COLUMN` 在回收之后，扫描结果少一行（30→29、2000→1999）。

**本次独立复核收敛出的两个候选机制**：

- **M1（链分叉）**：与 ISS22 **同一根因**——改写的两腿在页写满时分叉，改写副本落在孤儿页上 ⇒ 该行在链上不可见。**若 M1 成立，ISS24 由 D4 的修复一并关闭**。
- **M2（已回滚墓碑抑制前驱版本）**：墓碑的中性化 `VersionHeader::mark_aborted`（`src/transaction/version_chain.rs`）**保留链指针**（`next_version` 不清），只置 `create_tx_id = 0` + delete 哨兵。扫描路径的 `DataScanExecutor::superseder_suppresses`（`src/executor/data_scan.rs`）**识别** aborted 标记（`create_tx_id == 0` ⇒ 不抑制），但**以 `next_version` 链接构造抑制集合的活性规则不识别**：`src/storage/data/table_manager.rs` 的 `alter_drop_column` / `table_has_live_rows`、`src/executor/create_index.rs` 的回填、`src/wal/recovery.rs` 的 `rebuild_pk_indexes`——三处的 `pointed` 集合把**任何** `next_version` 目标都当作被指向的版本，不区分指向者是否已回滚。这违反**已验收**的 `mvcc-tombstone-visibility` R1（「未提交/已回滚墓碑 SHALL NOT 抑制、评估回溯前驱」）。

**决策**：

1. **RED 复现必须判别 M1 / M2**：判别方法（Act 按此执行，不新增判定层）——(a) 缺失行是否恰好是改写期跨过页容量边界的那一行（M1 预测：其改写副本落在链上不可达的页）；(b) 该行的版本链上是否存在一个**已回滚**的墓碑链接（M2 预测：存在，且指向者 `create_tx_id == 0`）。
2. **M1 若成立** ⇒ 由 D4 的修复关闭；ISS24 的验收断言是「改写后行数不减」。
3. **M2 无论是否为本次实测症状，一律修复**：它是对已验收 `mvcc-tombstone-visibility` R1 的违例（同一类缺陷，不同触发面）。修复形态：**抑制集合的构造只承认「指向者仍可能被读到且未被回滚」的链接**——即以指向者的 `create_tx_id` 是否为 0（aborted 标记）为准，与 `superseder_suppresses` 的既有判据同源。
4. **不得**以「只隐藏一行」为由把 ISS24 判为范围外。

**为什么必须同时保留 M1 / M2 两条线**：两者修复点不同（M1 在改写写的尾游标，M2 在活性规则的抑制集合），若只修其一而实测症状由另一条线造成，修复会「看起来通过」但缺陷仍在。判别步骤因此是 RED 用例的一部分，不是可选项。

## D6. B-4 的修复形态：释放路径改用有界读

**当前行为**：`drop_table`（`table_manager.rs:1408`）与 `truncate_table`（`:1836`）经 `collect_overflow_chain_pages`（`:1530`）扫描槽位里的溢出定位符，用 `SlottedPageRef::get_slot_data`（`src/storage/page_format/slotted_page.rs:125-129`：`&self.data[start..end]`，**无边界检查**）取槽数据 ⇒ 损坏页上越界切片 panic ⇒ 进程 abort。`DROP INDEX` 的释放路径同型。

**既有事实**：同文件的 `collect_data_chain_strict`（`:1720`）**已经**改用 integrity 模块的有界读（`check_data_page`），其文档注释明确写着「生产访问器索引 unchecked into a page and would panic on a damaged page，而重建在每次打开时运行、绝不能因损坏页崩溃」。**释放路径没有采用同一读法**。

**决策**：释放路径的槽位扫描改用**有界读**（与 `collect_data_chain_strict` 同一来源的 integrity 模块读法），损坏页按释放路径既有的 **best-effort 策略**处理（告警并跳过该页/该链，返回已收集的部分）——与 `collect_data_pages` / `collect_overflow_chain_pages` 现有的错误策略一致。

**为什么不改 `get_slot_data` 本身**：`get_slot_data` 返回 `&[u8]`（零拷贝），改成 `Option<&[u8]>` 会波及**全部**调用点（含热路径与恢复面），属于超出本 change 范围的重构。**为什么不把它降级为 panic-free 但静默**：`Option` 化的语义变化同样波及全部调用点。故选择**在释放路径换读法**，把 `get_slot_data` 的改动留给后续 change（作为范围外候选记录）。

**为什么不把释放路径改成「遇损坏页整体失败」**：释放路径的既有契约是 best-effort（物理释放是尽力而为），改成整体失败会改变 `drop_table` / `truncate_table` 的既有返回语义。**保持既有语义 + 不 panic** 是本 change 的边界。

## D7. ISS25 的修复形态：在途窄化状态对读路径可见，读路径显式拒绝

**当前行为**：`deserialize_tuple_width`（`src/storage/page_format/tuple.rs:204` 起）按位置解码：宽行忽略尾部多余字节，窄行尾部补 NULL 并返回实际解码列数，**不校验列序、不校验列数**。全部读路径（`DataScanExecutor` 的 `deserialize_row`）都走它。`ALTER TABLE DROP COLUMN` 的改写在提交点之前，数据面已经混入窄行，而目录仍是旧列数 ⇒ 窄行在旧目录下被读成「前 N-1 列按位置取值 + 尾部 NULL」⇒ ISS25 的 `[id, w, NULL]`。

**关键设计约束**：**不得改磁盘格式**。

- **行内列数标记方案（否决）**：给每个元组带列数/列序标记需要改 `VersionHeader` 或元组负载布局 ⇒ 旧代际库（G1/G2/G3 样本）的行将无法按原样解码 ⇒ **破坏 MS36 已验收的兼容面**（`legacy-format-compat` 的 G1/G2/G3 支持范围）⇒ 否决。
- **目录行新字段方案（否决）**：给 `__tables` 行加「在途窄化」字段会改变目录行布局代际 ⇒ 同样破坏 MS36 的代际定义（新增 G4 或改写 G3）⇒ 否决。

**决策**：**在途窄化状态只存在于内存中的表/目录状态**。

1. 改写开始时，DDL **发布**「该表正在从 N 列窄化到 M 列」的在途状态；
2. 改写完成（提交点）时**清除**该状态并窄化目录；
3. 读路径在读该表前**检查**该状态：处于窄化在途 ⇒ **显式拒绝**（返回明确的错误，如「表正在被修改，暂不可读」），**SHALL NOT** 返回任何按位置错读的值。

**为什么选「显式拒绝」而不是「等待改写完成」**：等待会在读路径引入新的阻塞语义（读语句挂起直到 DDL 完成），触及执行器生命周期与超时/取消语义（`statement-cancellation-outcome` 域）⇒ 范围与风险显著更大。显式拒绝是**有界、可测、无新阻塞语义**的形态。

**为什么「显式拒绝」优于「静默错读」**：ISS25 的危害是**静默返回错误的值**（读出 `[id, w, NULL]` 而调用方无从察觉）。显式拒绝把危害降级为「明确的错误」，是本 change 的可观察目标。

**改写窗口的边界**：在途状态覆盖「改写开始 → 提交点」这一段（含改写中途的崩溃前窗口）。**崩溃后的窗口**（在途状态是纯内存的，崩溃后消失）**当前无人承担**：活布局由 `apply_column_drop`（`src/storage/data/table_manager.rs:1215`）切换、目录由它窄化 ⇒ 若在「提交完成 → 目录应用」之间崩溃（活布局切换前）或该点之后语句被放弃（守卫析构 ⇒ 拒绝消失），重开后的活布局仍取自目录列行（旧列数）而数据面已是两宽的已提交行 ⇒ 读**仍按位置错位**。既有域 `ddl-catalog-transactional` R3 只覆盖「**放弃** DDL 之后重开库目录与数据面一致」，其一致性由 ISS22/ISS24 的修复（链一致 + 不隐藏行）承担——那两项承担的是**链一致与行可见性**，**不承担**提交点窗口内的「目录列数 ↔ 数据面行宽一致」。**本 change 不引入新的持久化状态** ⇒ 不扩大崩溃模型 ⇒ 该残余形态列为**范围外 Issue 候选**（关闭它需要持久标记 ⇒ 改磁盘格式 ⇒ 破坏 MS36 已验收的 G1/G2/G3 兼容面；或移动提交点 ⇒ 与 ISS21 / D5 的「被放弃 / 失败的 DDL 不留目录面变更」冲突）。**更正记录**：本段原称崩溃后的窗口「由既有崩溃模型承担 … 由 ISS22/ISS24 的修复承担」，该承担者陈述与实测证据矛盾，由 Iteration 003 的 Plan Review 2026-10-25 就地更正（**决策本身不变**：在途状态只在内存、不引入新的持久化状态、不扩大崩溃模型）。

## D8. B-1 的修复形态：刷盘失败保持脏标记 + 释放判定以持久为准

**当前行为**：`BufferPool::flush_all`（`src/storage/buffer_pool.rs:216`）与 `flush_all_except`（`:264`）在**第一阶段**（持锁拷贝页）就**清除脏标记**，第二阶段才写盘；写失败时 `?` 直接返回 ⇒ **失败页的脏标记已被清除且不会被重写** ⇒ 该页的内容可能从未落盘而内存里已「干净」。

释放的可分配判定（MS35 的 `free-page-lifecycle` R1）挂在 checkpoint 第 2 步：刷盘**开始前**取样「释放完成编号」，刷盘成功即提升、失败即丢弃。其隐含前提是「取样覆盖的释放，其锚点写必在本次刷盘前发出 ⇒ 本次刷盘必然把锚点写落盘」。

**B-1 的失效**：若锚点写所在的**另一次刷盘**（不在 checkpoint 内，例如 DDL 语句边界的有序落盘 `catalog.rs:269` `flush_commit_point`）失败，则锚点写**从未落盘**，而该页在内存里已「干净」；此后一次成功的 checkpoint 刷盘**不会重写它**（不脏），却仍会**提升**该释放 ⇒ **未持久化的释放被提前变成可分配** ⇒ 重开时该页既被新对象占用、又仍被旧目录登记 ⇒ 静默损坏。

**决策（两处）**：

1. **刷盘失败必须保持页的脏标记**（`flush_all` / `flush_all_except` / `flush_pages`）：写失败的页**恢复脏标记**，使下一次成功刷盘**必定重写**它。⇒ 锚点写不会因一次失败的刷盘而永久丢失。
2. **释放的可分配判定不得只以「锚点写已发出」为准**：checkpoint 第 2 步提升前，取样到的释放**不得在其释放完成之后发生过页写盘失败的情况下被提升**——那次失败的写可能落在锚点写所在页上，使「锚点写已持久」这一前提无法确认 ⇒ 该批释放**不提升**，并继续留在待释放集合（不被当作已丢弃而永久消失）。
   - **判据形态的实测定形**（Iteration 004 的 Plan Review 2026-10-25 独立确认）：本决策原先表述为「锚点写所在页**必须已不脏**」，两种取法都不可用——
     - **取样点取法**（该页仍脏 ⇒ 不提升）与 MS35 已验收的「`DROP` → checkpoint ⇒ 被释放的页在同一会话内被复用」**互斥**：`DROP` 的目录删除**不带落盘**（`Catalog::delete_table` 不调 `flush_commit_point`）⇒ 取样点上锚点页必为脏 ⇒ 该取法会拦掉 MS35 的既有提升；
     - **checkpoint 刷盘之后取法**判据**落空**：一次成功的 `flush_all` 之后不存在脏页 ⇒ 「不被提升」永不可观测。
     - ⇒ 两条流式在取样点的状态**完全相同**，唯一差别是**那次失败的写** ⇒ 唯一能同时满足两条验收面的信号是**失败历史**。
   - **闸门的实现形态**：限于既有机制——`FileStorage::promote_free_releases` 内以「最近一次写盘失败编号 > 该释放的完成编号」判否，编号取自既有 `release_id` 计数器（写失败与释放完成共用同一编号空间，编号单调 ⇒ 「失败发生在该释放完成之后」可由编号比较回答）。**无新 trait 方法、无持久状态、无磁盘格式改动、`free_page` 集合语义未动**；无释放生命周期的存储形态（默认空实现）零行为变化。

**为什么两处都要**：只做第 1 处 ⇒ 锚点写会在下一次成功刷盘时落盘，但**该次刷盘若不是 checkpoint**（例如又是一次 DDL 边界落盘），释放仍不会被及时提升（可接受，延迟到下一次 checkpoint）；第 1 处的残余窗口是「页已被驱逐出缓冲池」与刷盘并发的那一段（驱逐路径看到的脏标记已被刷盘的第一阶段清掉）⇒ 失败页的内容可能既没写盘也不在池内。第 2 处把「锚点写已持久」变成提升的**显式前置条件**：只要该释放完成之后发生过页写盘失败，就不提升 ⇒ 失败路径一律不进入可分配集合。

**与 MS35 已验收的 `free-page-lifecycle` R1 的关系**（原「为什么不改 R1 文本」的更正）：R1 的表述是「释放只有在其释放已被一次『在释放完成之后开始且成功完成』的 checkpoint 刷脏页持久化之后，才进入可分配集合」。本 change **收紧**该判定的实现，**不放宽**它 ⇒ 与已验收文本**不冲突**（收紧不需要改 R1 文本）。但收紧的**具体后果**须在新域 `release-durability-precondition` 中显式记录：**该释放完成之后发生过页写盘失败时，即使锚点写随后已被成功刷盘落盘，该释放在本次会话内也不被提升**（既有 R1 的场景「释放持久后页可分配」在该情形下不成立）。⇒ 新域承载这一更细的可观察面，docs-maintainer 合并时可与 `free-page-lifecycle` 并列保留。

## D9. B-3 不承载的理由

B-3 的形态是：DDL 语句边界的有序落盘（`catalog.rs:269` `flush_commit_point` → `flush_all_except` 写全部其它脏页）会把先前 `DROP TABLE` 的目录删除一并落盘 ⇒ `DROP TABLE` 的 checkpoint 边界不 survives 后续 DDL。

该形态**已被 MS35 已验收规格显式界定为范围外既有行为**：`drop-persistence-boundary` R1（MODIFIED）的崩溃点已改到「`DROP TABLE` 成功返回之后、任何后续 DDL 语句成功返回之前」，MS35 的 Task T8 与 `002-replan.md` 的 Plan Review 都记录了这一边界。修复 B-3 等于**推翻已验收的崩溃模型**并需要重新界定 `drop-persistence-boundary` 的保证面 ⇒ 属**新的范围决定**（需要用户裁定），不属缺陷承载。

⇒ **B-3 在本 change 记为「已被已验收规格显式界定为范围外既有行为，不承载」**，并在收尾交接清单中列为「若要改变该崩溃模型，须另立 change 并先取得用户裁定」。

## D13. 索引树读路径的损坏页语义：显式错误，不跳过

**当前行为**：`src/storage/btree/node.rs` 的索引树访问器族（`LeafNode` `:86`/`:98`、`LeafNodeRef` `:555`/`:565`、`InternalNode` `:673`/`:685`、`InternalNodeRef` `:1041`/`:1051`）用 `SlottedPageRef::get_slot_data` 无边界地切页内字节 ⇒ 损坏的索引页在**读 / 写热路径**（`index_manager.rs:299-346`、`:532-540` 的索引下降与条目提取）上越界切片 panic ⇒ 进程 abort。与 B-4 **同根因层**，但 B-4 的释放路径已在 Iteration 002 闭合；本条是**读 / 写路径**。

**决策**：损坏的索引页在读 / 写路径上给出**明确的错误**（点名损坏的页与索引），SHALL NOT abort；未损坏路径的读 / 写行为零变化。

**为什么不复用释放路径的「告警 + 跳过」**：释放路径跳过损坏页是**既有契约**（物理释放尽力而为，见 D6；`collect_all_pages_tolerant` 的既有注释即写明损坏结点的子树「leaked by design, warned」）。读路径**不能**照搬：跳过损坏的内部结点 ⇒ 下降无法确定子结点 ⇒ 若当作「没有这个子树」继续 ⇒ 点查返回「查不到该行」⇒ **静默错读**（比 abort 更隐蔽的错误形态）；若任选一个子结点继续 ⇒ 读到**别的行**。⇒ 读路径只有两种安全形态：**明确错误**或**进程 abort**；本 change 取前者。

**为什么不改 `get_slot_data` 的签名**：同 D6 —— 改成 `Option<&[u8]>` 会波及全部调用点（数据页 / 目录页 / 恢复面 / 缓冲池，同形态共约 25 处），属超出本 change 范围的重构；本条在**索引树访问器族**的调用点收口。

**范围界定**：本 Iteration 只覆盖**索引树访问器族**（`node.rs`）与其调用点的错误语义。存储层其余同形态无界读点（数据页 / 目录页 / 恢复面 / 缓冲池，约 17 处）各自的「损坏页正确行为」不同（目录页：是否拒绝打开？数据页：跳过该行还是整体失败？恢复面：如何处置该页？），需要各自的调查与设计决定 ⇒ 不并入本 change，登记为 Issue 候选由 Recorder 承载（另立「存储层有界读」专项 change）。

**与 D6 的关系**：D6 治**释放路径**（尽力而为 ⇒ 跳过），本条治**读 / 写路径**（正确性 ⇒ 显式错误）。两者对损坏页的**处置方向相反**，因此必须分属不同 Iteration，不能合并成一个「统一的有界读」任务。
