# Design：MS35 空闲页跨重启复用

本文件记录长期技术选择及其理由，随 change 归档。实施依据在 `iterations/000-reopen-free-page-reconstruction/000-initial.md` 的 Plan Context。

## D0. 术语与不变量

- **释放（release）**：一个已登记对象（表 / 索引 / 溢出链）的页被归还给存储层的空闲集合。释放**不写零页**（沿用 MS33 D1：清零发生在空闲页被再次分配时，不在释放时）。
- **持久空闲页（durable free page）**：在崩溃边界上已经空闲的页——即**持久目录不再引用**它，且它的原主人已经不在持久目录里。
- **可分配页（allocatable page）**：当前会话可以交给新对象使用的页。
- **不变量 N1（本 change 的核心）**：一个页成为可分配页，当且仅当「它的释放在崩溃边界上已经成立」。⇒ **未完成的释放永远不是可分配页**，无论崩溃前还是崩溃后。
- **不变量 N2**：可分配页集合中的页，持久目录一定不引用它。⇒ 可分配页被交给新对象时，不会摧毁任何持久对象的页内容。

## D1. 路线评估：打开时安全重建 vs 持久空闲页管理

MS35-T01 与 I087 明确不把「把内存空闲列表原样序列化成持久格式」当作唯一方案。两条候选路线的关键差别在**空闲集合与所有权是否同源**。

### D1.1 候选 (b)：持久空闲页管理（单独持久化空闲集合）

把空闲集合单独持久化（伴生文件或数据文件内的独立结构），打开时读回。问题出在**两次独立持久化之间的一致性**：

- 目录登记与空闲集合是两次独立写入。设上一次 checkpoint 后页 P 空闲；本会话把 P 分配给新表 u；本会话 checkpoint 时若先把空闲集合写成「P 不空闲」、再刷目录，则顺序无害；反之若目录先落盘、空闲集合仍是旧的（仍称 P 空闲），崩溃后重开得到「持久目录拥有 P」且「持久空闲集合也含 P」⇒ P 被交给下一个对象 ⇒ **持久对象的数据被摧毁**。
- 要在**不做可达性遍历**的前提下消除这个窗口，必须保证「空闲集合的持久化永远不晚于目录的持久化」。但 checkpoint 第 2 步是多页无序刷盘（`src/storage/buffer_pool.rs:216-233`：先收集脏页再逐页写），**同一份脏页集合内部没有跨结构写序保证**；要把空闲集合页强制排在目录页之前写入，就要绕过缓冲池直接写文件（与缓冲池内的旧副本互相覆盖），改动面与风险都显著高于本 change 的预算。
- 另一条等价出路是让空闲集合**滞后于**目录（即只写「已经确定空闲」的子集）。这同样要求逐次判定「哪些释放已经确定空闲」，而「确定」又依赖目录的持久化状态 ⇒ 回到可达性遍历。
- 此外，(b) 需要**新增持久产物**：伴生文件要进 CLI 的文件族删除（`src/cli/lifecycle.rs:153-161` 只处理 `.wal` / `.checkpoint` / 主文件）与状态列举，要考虑加密语义与备份语义，并牵动格式版本与 MS36 的历史库兼容面。

**结论 (b) 排除**。根本原因：它把「谁拥有这一页」和「这一页空闲吗」拆成两份可独立失步的持久状态，而本 change 要的恰恰是两者**永不失步**。

### D1.2 候选 (a)：打开时按持久目录安全重建

空闲集合 = 「持久目录引用不到的页」。所有权与空闲判定**同源同一次推导** ⇒ 二者在崩溃边界上天然一致，不需要任何跨结构写序，也不需要新的持久产物。

代价与对策：

| 代价 | 对策 |
|---|---|
| 必须枚举**全部**页所有者，漏一个就把活页判成空闲页（静默损坏） | 所有者集合由 `allocate_page` 的全部调用点穷举确定（见 D3.1）；重建的活页集合用与 `drop_table` 释放路径**同一套**遍历原语（对称性：被 `drop_table` 释放的页正是重建不会判成空闲的页）；新增回归用例钉住「重建出的空闲集合恰好等于被释放的页集合，且不含任何活表页」。 |
| 遍历出错（读错误）时可能把活页误判为空闲 | **失败安全**：任一次遍历失败 ⇒ **整次重建放弃**，本次打开的可分配页集合为空（只降级不复用，绝不误判）。见 D3.4。 |
| 打开时多走一遍活页（性能） | 遍历只读、只做一次；读只读会话不需要它（只读会话不做页分配），实现上只在读写打开路径触发。 |

### D1.3 选定组合

**选定 (a) 打开时安全重建**，并**叠加**「释放的持久化判定」（D2）。两者缺一不可：

- 只有 (a) 而没有 D2：重建解决了**崩溃之后**的空闲集合来源，但会话内仍会把「未完成的释放」立刻交给新对象——新对象把该页清零，而持久目录仍登记着旧主人 ⇒ 崩溃后旧主人的数据静默消失。**这正是 MS33 R1 末句留给本阶段的窗口**，只做 (a) 等于把这个窗口原样留下。
- 只有 D2 而没有 (a)：会话内的释放时机正确了，但跨重启的空闲集合仍然丢失 ⇒ MS35 的承诺（跨重启复用）不成立。

## D2. 释放的持久化判定（会话内释放的生命周期）

### D2.1 当前行为

`FileStorage::free_page`（`src/storage/file_storage.rs:490-498`）把页号直接推进 `free_pages`；`allocate_page`（`:435-458`）弹出时写零页。同一次打开内，被释放的页立即可分配——**无论该释放是否已经持久**。

### D2.2 目标行为

一个被释放的页先进入**待释放集合**，只有当它的释放**在崩溃边界上已经成立**之后，才进入可分配集合。

「释放在崩溃边界上成立」的可判定条件（本项目的事实基础）：

- DDL 不写任何 WAL 记录（`src/wal/checkpoint.rs:154` 的既有结论）⇒ **DDL 的持久性完全由目录页的刷盘决定**。
- 崩溃模型是**进程内丢弃句柄且不调用 close**（脏页丢失），不是真实断电（`openspec/specs/drop-persistence-boundary/spec.md` Purpose）⇒ 「写进数据文件」即等价于「已持久」，不需要 fsync 级别。
- 因此：一个释放的锚点写（`DROP TABLE` 的目录删除、`DROP INDEX` 的目录摘除、`TRUNCATE` 的表头原地重置 + 目录尾指针更新）**被 checkpoint 第 2 步成功刷盘**之后，该释放即成立。

### D2.3 机制

存储层持有三个状态：

```text
free_pages      : 可分配页（持久空闲 + 已提升的释放）
pending_frees   : 待释放集合，元素 = (释放编号, 页号)
release_id      : 已完成释放的计数（单调递增）
```

- `free_page(p)`：把 `(当前释放编号, p)` 记入 `pending_frees`，**不**进 `free_pages`。
- `complete_free_release()`：释放操作**完成**时调用一次，把 `release_id` 前进一格——即「本次释放的锚点写已经发出」。
- checkpoint 钩子（`src/wal/checkpoint.rs` 第 2 步刷脏页前后）：
  - 刷盘**开始前**记下 `limit = release_id`；
  - 刷盘**成功后**：把 `pending_frees` 中释放编号 `< limit` 的项提升进 `free_pages`；
  - 刷盘**失败时**：把 `pending_frees` 中释放编号 `< limit` 的项**丢弃**（不提升）。

### D2.4 为什么用「释放完成编号」而不是「页号入队序号」

刷盘开始前记 `limit` 这一步同时排除两种竞态：

- **释放发生在刷盘期间**：它的释放编号 ≥ `limit` ⇒ 本次不提升 ⇒ 它的锚点写没有参与本次刷盘 ⇒ 不能提升 ✔。
- **锚点写晚于释放动作本身**（`TRUNCATE` 的形态：先释放尾页与溢出链页，再原地重置表头、再更新目录尾指针，见 `src/storage/data/table_manager.rs:1602-1625`）：若按「入队序号」判定，本次刷盘可能没有包含那次表头重置，而尾页已被提升为可分配 ⇒ 崩溃后持久目录仍指向旧链，而旧链的尾页已被新对象清零 ⇒ 结构损坏。用「释放完成编号」后，提升的前提是「释放**整体完成**（含锚点写）之后才开始的刷盘」⇒ 那次刷盘必然包含锚点写 ✔。

**代价**：`TRUNCATE` 的既有崩溃语义（`truncate-table` 规格记录的「部分清空」形态）不变——MS35 只收紧「被释放的页何时可分配」，不改 `TRUNCATE` 自身的崩溃结果。

### D2.5 为什么刷盘失败要丢弃而不是保留

刷盘失败时 `BufferPool::flush_all` 已清掉脏标记（`src/storage/buffer_pool.rs:221-223` 先清标记再写），失败页的内容**不会重试** ⇒ 该释放的锚点写可能永远没有落盘。若仍保留待释放项，下一次成功刷盘会把它们提升为可分配，而持久目录仍登记着旧主人 ⇒ N1 被破坏。**丢弃**（本页泄漏到本次会话结束）是唯一保守方向：磁盘上这些页仍归旧主人所有，重开时重建也会把它们判成活页 ✔。

### D2.6 对既有可观察行为的影响（诚实声明）

同会话内的页复用从「释放后立即」变为「释放持久后」（需要一次成功 checkpoint）。这是本 change 唯一的行为回退面：

- `drop-table-physical-free` 规格的「同进程 free-list 复用」要求因此被 MODIFIED。
- 既有断言受影响的位置（全部需要更新，断言语义保留）：
  - `tests/drop_table_free_test.rs` 的 5 个同会话复用断言（`test_simple_drop_releases_data_and_btree`、`test_long_data_page_chain_all_released`、`test_btree_height_gt_1_all_pages_released`、`test_same_process_free_list_reuse`、`test_concurrent_drop_different_tables`）——插入一次 `db.checkpoint().await` 作为分界（释放持久化之后再复用）。
  - `tests/overflow_page_test.rs::truncate_releases_overflow_chain_pages_keeps_definition`——断言「链页被立即清零并合法复用为新 PK 根」，改为「链页在释放持久化之后才可复用」。
  - `src/storage/page_format/overflow.rs::free_overflow_chain_returns_pages_for_reuse`（lib 单测）——断言「释放的链页立即可复用」，改为「释放进入待释放集合，持久化后才可复用」。
- `overflow-page-storage` 域的「溢出页链 SHALL NOT 产生孤儿页」要求**不受影响**（该域规定的是释放点的存在与无孤儿页，不规定复用时机）✓ 无需 MODIFIED。

### D2.7 释放点清单（全部释放点都必须调用「释放完成」）

| 释放点 | 位置 | 锚点写 |
|---|---|---|
| `DROP TABLE` | `src/storage/data/table_manager.rs:1389+`（`drop_table`） | 目录删除（先于释放） |
| `TRUNCATE TABLE` | `src/storage/data/table_manager.rs:1590+`（`truncate_table`，释放在 `:1602-1615`、表头重置在 `:1617-1620`、目录尾更新在 `:1624-1625`） | 表头原地重置 + 目录尾指针更新（**晚于**释放） |
| `DROP INDEX` | `src/executor/drop_index.rs:62-63` | 目录摘除 |
| GC 清理旧版本（含溢出链） | `src/storage/data/table_manager.rs:170` → `src/storage/data_page.rs:249`（`delete_tuple_from_data_page` → `free_overflow_chain`） | 旧版本 slot 的移除（数据页写） |
| `CREATE INDEX` 回填失败清理 | `src/executor/create_index.rs:83` | 无（该索引从未登记）⇒ 释放无锚点，其可分配时机同样等下一次成功刷盘（保守方向，无害） |
| 溢出链写入失败清理 | `src/storage/page_format/overflow.rs:140`、`src/storage/data_page.rs:81` | 无（同上） |

**为什么 GC 路径也必须纳入**：GC 移除旧版本 slot 是一次**数据页写**（不经 WAL 记录）。若链页在这次写落盘前就被复用，崩溃后旧版本 slot 仍在、locator 指向已复用的页 ⇒ 版本链读出错。因此 GC 的释放与 DDL 的释放受同一条规则约束（锚点写落盘后才可分配）。

**为什么失败清理路径也纳入**：这些页在本会话内分配且从未登记进目录，释放它们本身没有锚点；把它们与其它释放一并推迟到下一次成功刷盘，是唯一不需要额外状态的方向（代价是本会话内的一次延迟复用）。

## D3. 打开时按持久目录重建空闲页集合

### D3.1 页所有者的穷举

`allocate_page` 的全部调用点（本次调查逐一核对）：

| 调用点 | 产生的页 | 归属 |
|---|---|---|
| `src/storage/catalog.rs:155`、`:162` | 页 0 / 页 1 | 目录链（`__tables` / `__columns`） |
| `src/storage/catalog.rs:682` | 目录链续页 | 目录链 |
| `src/storage/data/table_manager.rs:451` | 表数据页头 | 表数据链 |
| `src/storage/data_page.rs:56` | 数据链续页 | 表数据链 |
| `src/storage/page_format/overflow.rs:155` | 溢出链页 | 行槽 locator 指向的溢出链 |
| `src/storage/btree/btree.rs:108`、`:214`、`:263`、`:344` | B-Tree 根 / 分裂页 | 索引树（PK / 唯一 / 二级） |

⇒ **四类所有者**：目录链、表数据链（含溢出链）、三类索引树。视图不拥有页（`open_or_init` 跳过视图行，`src/storage/data/table_manager.rs:281-283`）。

### D3.2 活页集合的组成

重建必须覆盖：

1. **目录链**：`__tables`（页 0）与 `__columns`（页 1）两条链，按 SlottedPage 的 `next_page_id` 走到链尾。
2. **每个基表的目录行所指向的**：数据链（从 `data_page_head`）、溢出链（数据页槽内 locator 指向的链页）、PK 树（`index_root_page_id`）、唯一索引树（`unique_roots`）、二级索引树（`secondary_indexes[].root`）。
3. **内存中索引管理器的全部页**（`IndexManager::collect_all_pages`）：恢复重建索引树后，内存树的根与持久目录登记的根可能不同（恢复期的换根**不**持久化，`src/storage/data/table_manager.rs:305-314` 与 `src/database.rs:424-427`），两者的页都必须算活页 ⇒ 取**并集**。

遍历原语复用既有实现（与 `drop_table` 的释放路径同型）：`TableManager::collect_data_pages`（`:1477+`）、`TableManager::collect_overflow_chain_pages`（`:1512+`）、`IndexManager::collect_all_pages`（`src/storage/btree/index_manager.rs`）。

### D3.3 空闲集合的边界

- 空闲集合 = `[0, page_count)` 减去活页集合，其中 `page_count` 取**重建时刻**的 `storage.page_count()`（`src/storage/file_storage.rs:512-514`）。
- 重建期间新分配的页不在活页集合里 ⇒ 必须用重建开始时的页数上界，否则会把刚分配的页判成空闲。⇒ 实现上先取 `page_count` 快照再遍历。

### D3.4 失败安全

任一遍历返回错误（页读失败、树页类型异常等）⇒ **整次重建放弃**：不向空闲集合注入任何页（本次打开的可分配页集合为空），并记录一条可观察的告警。后果：本次打开不复用任何释放空间（降级），但**绝不会**把活页判成空闲（不损坏）✔。

### D3.5 触发点

`src/database.rs::open_internal` 中，读写模式分支内、`attach_index_catalog_contexts()` 之后（`:427`）——必须在恢复之后，因为恢复会重建索引树并分配新页。只读模式不做页分配，不需要重建；内存模式无文件页空间。

## D4. MS33 遗留窗口的可观察结果

MS33 的 R1 末句把「同会话页分配复用被释放页后、在分配方语句的 catalog 落盘之前崩溃」的窗口交给本域。结果规定为：

- **未完成的释放在任何时刻都不是可分配页**（N1）⇒ 该窗口**不再以「旧表数据被清零且不可恢复」的形式出现**。
- 崩溃后重开：持久目录仍登记旧主人（它的删除未落盘）⇒ 旧主人的已提交行**仍可查询**，完整性检查无 error 级发现。MS33 描述的窗口在本闸门下**不可达**：释放在崩溃边界上成立之前，被释放的页不会被任何新对象取用（N1），因而不存在「分配方对象在重开后消失」的可观察形态。旧对象在重开后是否仍可见，取决于崩溃点是否落在任何后续 DDL 语句成功返回之前（DDL 的语句边界有序落盘会把该语句的提交点与其它脏页一并落盘，先前的目录删除因而随之落盘）——该崩溃模型的归属见 `drop-persistence-boundary` 域。
- 同一会话内「释放后立刻建表」的既有要求（`drop-persistence-boundary` R2）仍然成立：新表拿到的是**空页**（无论是复用的持久空闲页还是新页），只含新插入的行。

## D5. 实现顺序与依赖

1. **T1 重建**：先写 RED 用例（跨重启复用）→ 实现活页集合重建 + 打开钩子 + trait 接缝 → GREEN。此阶段可分配集合只含「持久空闲页」。
2. **T2 持久化判定**：先写 RED 用例（崩溃窗口 + 释放持久后才可分配）→ 实现待释放集合、释放完成编号、checkpoint 钩子、全部释放点的完成标记 → GREEN；同时更新既有同会话复用用例的断言分界。
3. **T3 端到端回归**：把跨重启复用、崩溃窗口、失败安全、重开后可读性汇总成独立回归文件，补齐 `check_integrity` 断言。
4. **T4 收尾**：M19 分批串行全量回归（见 change `tasks.md` 的收尾验证段）。

## D6. 明确禁止的实现方式

- 不得引入身份证明机制（Hash/指纹、revision pin、run-id、artifact manifest、日志 Hash 链、时间顺序证明等）与其采集/审计工具（AGENTS.md 行为约束）。
- 不得在 `cargo test` 之外建判定脚本、封装命令、专用参数或判定层。
- 不得用 timer 阈值作行为判据（若需要等待，用可观察状态 + `yield_now` 轮询，timer 只作夹具失控兜底）。
