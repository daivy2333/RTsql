## Why

里程碑 MS52（`.agents/docs/tasks.md`）要求先量到撕裂树的恢复代价，再决定改刷盘、改驱逐还是维持现状；同时决定跨进程一写多读的场景是否成立。I031 里的 40k 行 8.86s、160k 行 40.7s 来自 2026-09-08 的 debug 标定，不能当作当前代价。I084 要求先看锁等待，再决定要不要写快照协议。

## What Changes

- 在 `0019bf1` 的 release 构建上测量不洁重开和检查点后的再次打开，并核对行数。
- 测量写锁持有期间的只读 CLI。持锁时退出码 4；放锁后读到已提交行。
- 维持 `BufferPool::evict_one` 的时钟淘汰、`flush_all` 的池遍历顺序，以及 `redo_count > 0` 时不消费磁盘 B 树、重放后重建索引。
- 维持读写独占锁和只读共享锁。不写跨进程快照、缓存失效或新的检查点协议。
- 不修改 `src/` 和 `tests/`。不建第二个变更。

### 场景草图

1. 一万行不洁重开。前置：release，默认 100 页池，`tests/cli_test.rs` 的 `build_big_wal`（表 `t(id INT PRIMARY KEY)`，50 行一个显式事务，drop 且不 `close`）。动作：`Database::open` 后 `SELECT COUNT(*)`。结果：打开成功，行数为 10000，这次打开 537ms。日志有旧索引页类型 `0x00`、跳过子树，以及空闲页集合重建放弃。失败边界：打开失败或行数不是 10000 时，这次计时不能支持维持结论。
2. 四万行不洁重开。前置与动作同场景 1，`N=40000`。结果：行数 40000，打开 3.814s，同样出现非法页类型和空闲页重建放弃。失败边界同场景 1。
3. 检查点后再打开。前置：场景 1 或 2 已经 `close`，并且 `Database` 已经 drop。动作：再次 `Database::open` 和 `SELECT COUNT(*)`。结果：10000 行用 25ms，40000 行用 100ms，行数不变，这次打开不再打印非法页类型。失败边界：句柄还活着就再次打开，得到 `DatabaseLocked`，那一次不算检查点后的打开。
4. 持锁时的只读命令。前置：库里有一行，另一进程对主文件持有独占 flock。动作：`rtsql --busy-timeout 300 --readonly <path> "SELECT id FROM t"`。结果：退出码 4，306ms，stdout 为空，stderr 含 `database is locked`。失败边界：持锁期间退出码 0 或读到行，则「读者被文件锁挡住」不成立，回到计划。
5. 放锁后的只读命令。前置：独占锁已释放，库由正常退出的 CLI 做过检查点。动作：不带 `--busy-timeout` 的同一条只读命令。结果：退出码 0，5ms，读到该行。失败边界：放锁后仍报锁定，则现有等待预算没有放行，回到计划。
6. 维持合同。前置：场景 1 到 5 的结果。动作：结束本变更的产品修改。结果：刷盘、驱逐、恢复门控和文件锁保持测量前的代码。失败边界：若缩短恢复时间必须改掉整棵重建，或读者必须在写者持锁时成功，这两项都不在本变更实施。

### 已经由目标和测量选定的行为

- 恢复代价按 `Database::open` 的墙钟计，构建是 release。分子不是单独拆出来的重建函数时间。行数必须等于插入行数。
- 刷盘顺序和 no-steal 都不进入「有重放就重建索引」的路径。它们不能缩短场景 1 和 2 的打开时间。不改这两处。
- 每次提交都做全量检查点会把刷盘成本挪到正常提交上。本次没有测量那个成本，不把它当成已经值得做的刷盘改动。
- 「场景成立」指当前已经支持的入口要求：写者进程仍持有数据库时，另一进程读到已提交行。CLI 在命令结束时 `close` 并随进程退出放锁。没有 `rtsql serve`。因此场景不成立，保持现有文件锁。
- 重放路径改为增量维护索引、从而跳过整棵重建，超出本里程碑点名的刷盘和驱逐合同。不纳入本变更。

这些判定在本目标范围内，按批准使用，不是跳过。
