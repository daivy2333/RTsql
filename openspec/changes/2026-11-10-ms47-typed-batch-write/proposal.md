# MS47：按测量决定类型化批量写入入口的去留

来源：里程碑 MS47（`.agents/docs/tasks.md`，Status ready），承接 I021。关联约束：M21、M22。测试执行约束以本次 goal 为准，高于本分支已提交的 M19 中「单次目标验证可用默认并行度」那一句。

Gate 1 为 PASS。批准来自本次 goal 对需求与范围的批准。本文件不更新里程碑状态，不改 SNAPSHOT，不改 project-model，不改 `openspec/specs/` 里的权威正文。

## Why

导入攒批和 CSV 去掉逐行 SQL 文本都要复用同一条写入口。当前引擎还没有这条类型化批量写入入口，也没有一次按统一诊断口径记下的「逐行插入占端到端写入多少」的测量。占比低于 10% 时，即使把逐行插入成本降到零，端到端也改善不到 10%，入口不值得新增。

## What Changes

- 用已交付的统一诊断，对现有插入基准的语句形状做一次测量，并把比例与「建入口」或「不建入口」写入本变更产物。
- 比例 ≥ 10% 时，新增 `Database::insert_batch`。类型检查、约束、索引维护和失败回滚与逐行 `INSERT` 一致。整批失败则整批回滚。
- 比例 < 10% 时，不新增入口。SQL `INSERT` 保持现状。
- 无 **BREAKING**。不改磁盘格式，不改 SQL `INSERT` 的结果、错误文本和 SQLSTATE。

## Capabilities

### New Capabilities

- `typed-batch-write`：本次测量如何决定入口去留；入口交付时，批量写入与逐行插入在类型、约束、索引和整批回滚上的可观察合同。

### Modified Capabilities

无。`sql-write-surface`、`dml-transaction-lifecycle`、`unified-diagnostics` 的既有 Requirement 不改。测量只读取诊断摘要，不改诊断口径。

## Impact

- 测量轮只新增一个集成测试，产品代码不动。
- 入口轮（仅当测量达到门槛才展开）会新增 `Database::insert_batch`，并在语句管道里复用现有的隐式事务 DML 臂和 `InsertExecutor`。不改 `InsertExecutor` 的逐行检查顺序。
- 不接入 import 与 CSV。不改分配器、clone、节点锁、io_uring、组提交、代价模型和 JOIN 重排。
- 关联：MS47；I021。M21 把新的公共入口放在 `Database`。M22 规定诊断只观察，本变更不把诊断摘要当作 SQL 结果的判据。

## 回滚

测量轮只增加测试文件。回滚时删掉该测试，引擎行为与变更前相同。

入口若已交付，它是加在 `Database` 上的新方法，SQL 路径未改。回滚时删除该方法、管道上的对应函数和它的测试。已有库文件不需要迁移。

## 采纳条件

本次 goal 已写死，计划不再改门槛：

- 逐行插入耗时占端到端写入耗时的比例 ≥ 10% 时，交付类型化批量写入入口。
- 该比例 < 10% 时，不新增入口，只把测量与「不建入口」写进变更产物。
- 比较使用整数：`insert_exclusive_ns * 10 >= total_ns` 为达到门槛。总耗时为 0 时测量无效，不把它当成未达到。
- 理由：占比低于 10% 时，即使把逐行插入成本降到零，端到端也改善不到 10%。本仓库 MS32 用 10% 时间门决定一条批量路径留还是撤。口径不同：MS32 比的是新路径是否比旧路径快 10%，本次比的是旧路径在端到端里占多少。

## 测量口径

里程碑要求测量使用已交付的统一诊断和现有基准。现有端到端插入基准是 `benches/scale_bench.rs` 的 `scale_insert`，语句形状在 `benches/common/mod.rs` 的 `insert_rows`：对 `CREATE TABLE bench (id INT PRIMARY KEY, name STRING, value INT)` 之后的表，逐条执行 `INSERT INTO bench VALUES ({i}, 'user_{i}', {i * 10})`。`scale_insert` 的最小档是 1000 行。每条 SQL 文本不同，计划缓存全部未命中。

本次只测这一档、只跑一遍，构建用 `cargo test --release`。`cargo bench` 继承 `[profile.release]`（`opt-level = 3`，`lto = true`）。不跑 criterion 的重复采样，因为采样总时间包含开库、建表和删文件，而且会把同一次插入重复许多遍。不测 10000 与 100000 档：语句形状与 1000 档相同，100000 档有机会越过默认 16 MiB 自动 checkpoint，把检查点写进一部分提交。

统一诊断已定义插入语句的耗时拆分（`openspec/specs/unified-diagnostics/spec.md`，场景「插入的提交是执行的子阶段」）：

- 端到端写入耗时 = 这 1000 条 INSERT 摘要的 `Summary.total` 之和。`total` 是根阶段包含耗时。
- 逐行插入耗时 = 这 1000 条摘要里执行阶段 `exclusive_total` 之和。执行阶段独占耗时 = 执行包含耗时 − 提交子阶段包含耗时。提交是执行的子阶段。
- 建表在打开诊断之前执行，不进入上述和。开库和删文件不进入上述和。

`DiagnosticsConfig.summary_limit` 默认 32。测量配置把它设为 1000，并只打开 `collect.stats`，以便 1000 条摘要都留下。

## 场景草图

### 测量达到门槛

- 前置状态：空库，诊断尚未打开。
- 动作：建好 `bench` 表，打开诊断，按上述口径插入 1000 行，读回摘要并计算比例。
- 可观察结果：1000 条 INSERT 摘要都在；比例 ≥ 10%。变更完成后存在 `Database::insert_batch`。
- 失败边界：摘要不足 1000 条、缺 parse / plan / execute / commit，或总耗时为 0。此时测量无效，不交付入口，也不把缺测当成「低于 10%」。

### 测量未达门槛

- 前置状态：同上。
- 动作：同上。
- 可观察结果：比例 < 10%。变更产物写下测量数字和「不建入口」。公共 API 不新增批量写入方法。SQL `INSERT` 的结果与错误保持。
- 失败边界：同上一场景的无效测量。

### 入口交付后的成功写入

- 前置状态：入口已交付。表已存在，调用方持有与表列顺序等宽的 `Value` 行。
- 动作：一次 `insert_batch` 写入多行。
- 可观察结果：受影响行数与随后的 `SELECT` 行，同一次等价的多行 `INSERT INTO t VALUES (...), (...)`。
- 失败边界：只读会话、未知表、视图名、行宽不符在任何写入之前拒绝，表内容不变。

### 入口交付后的整批失败

- 前置状态：入口已交付。表里可以已有已提交行。批量的某一行会在类型、NOT NULL、主键、UNIQUE 或二级索引上失败。
- 动作：一次 `insert_batch`。
- 可观察结果：调用返回与等价多行 `INSERT` 相同的错误文本和 SQLSTATE。本批每一行都不可见。批之前已提交的行仍在。
- 失败边界：出现部分行可见时，本变更停止并回到需求裁定。不把语义改成部分成功。

### 空批与显式事务并存

- 前置状态：入口已交付。表存在。
- 动作：传入零行；或调用方已 `begin` 一个显式事务，再调用 `insert_batch`。
- 可观察结果：零行调用返回受影响行数 0，不写入。显式事务仍由调用方提交或回滚；`insert_batch` 成功写入的行不随该显式事务的回滚消失。
- 失败边界：零行调用留下 WAL 事务，或 `insert_batch` 把行写进调用方的显式事务。

### 取消

- 前置状态：入口已交付。索引写暂停点装在结构变更之后、根页发布之前。
- 动作：两行批量在第二行到达暂停点时丢弃 future，再执行另一条隐式写以触发回收。
- 可观察结果：两行的键都可以再次插入。批之前已提交的行仍在。
- 失败边界：取消后有一批中的键永久占用，或进程中止。

## 缺口处理

下列边界已由里程碑正文、采纳条件和现有代码合同定下，不另作开放问题：

- 工作负载用现有 `insert_rows` / `scale_insert` 的单行 `execute_sql`，不用一条多值 `VALUES` 语句。多值 `VALUES` 不是现有端到端插入基准。
- 分母用诊断摘要的语句总耗时，不用 criterion 闭包总时间。
- 构建用 release profile，与 `cargo bench` 继承的 release 配置一致。
- 空批返回受影响行数 0 且不开启事务。同一先例是空源 `INSERT SELECT` 返回受影响行数 0。
- 入口是一次独立调用，自带隐式事务，与 `execute_sql` 的 `INSERT` 相同。不加入调用方已经 `begin` 的显式事务。
- 表名按 catalog 与视图注册表中的存储名精确查找。入口不解析 SQL，不做标识符大小写折叠。
- 行必须与表列等宽、按表列顺序。列清单、`DEFAULT` 关键字、表达式和 `ON CONFLICT` 留在 SQL 路径。

失败语义若要改成部分成功，先回需求裁定。本提案不接受这种缺口。

## 测试约束

任何测试调用都带 `--test-threads=1`。多个测试目标逐个执行。

本 change 的全部 Iteration 都不安排全量测试，规划与实施也不跑全量。用户原话：「这次自动化把全量测试放到最后来限制全量的次数」。全量在 MS46 与 MS47 都收尾合回主分支之后，按 `.agents/runbooks/m19-batched-full-regression.md` 分批串行，只跑一次。

风险：本 change 收尾前没有全量。合回后那一次失败时，排查范围包含 MS46 与 MS47。
